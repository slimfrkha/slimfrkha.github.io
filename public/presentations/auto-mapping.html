The product problem

Every website needs a mapping

A mapping = a set of page groups

Each page group gathers similar pages, is built with rules on the URL, and is assigned a page category.

Rules use the product's operators

contains, does not contain, exactly matches, begins with, ends with, regex… on the path, the query or custom variables, combined with AND / OR.

Why it matters: a mapping is the logical view of a site that analyses build on: journey analysis, and any automatic analysis that needs page context.

The modeling solution · Design choices

Two choices that shape the solution

Choice 1

Cluster, then describe

Group similar URLs without labels, then write rules for each group. The output has the shape of a mapping: groups, rules, categories.

A first attempt classified single URLs into page categories with a character-level CNN over path, query and custom variables. It performed poorly on several categories, and a per-URL label gives neither groups nor rules.

Choice 2

Measure against human mappings

Clustering becomes a pairwise classification: for each pair of URLs, are they in the same reference page group, and in the same proposed group?

per website w: F1w = ½ (F1same + F1different)
score = mean of F1w over validation websites

Validation websites are never used to build anything, so the score measures websites the system has never seen.

The modeling solution · First version

First version: a plain URL distance and a silhouette cut

1

Sample 1,000 URLs per website.

2

Distance, field by field: same host? same value at each path level? how many shared query and custom-variable keys, with equal values? Normalized over levels, keys and URL parts, bounded in [0, 1]. Every term weighs the same.

3

Hierarchical clustering builds a tree (a dendrogram) over the URLs.

4

Cut the tree: try every number of clusters between 10 and 40, and keep the one with the best silhouette score.

5

Write rules for each cluster.

The modeling solution · First version

Why the first version breaks

Illustrative tree: the cut gives product groups split by locale, and groups mixing page types.

The distance is blind to meaning

A match on an ID or a locale counts as much as a match on product. For example, two product URLs are 0.21 apart, and a product and a cart only 0.43.

The cut is blind to meaning

The number of clusters comes from the silhouette score, a geometric criterion. The splits that matter, like product versus cart, can sit anywhere in the tree, even at the very bottom: groups come out fragmented, or mixing page types.

Both need to know which terms matter: the second version adds a term library.

Build the library

1

Extract the terms used in the rules of reference mappings, from training websites only.

2

Annotate their importance by hand, with a page category when it is clear. The flywheel keeps adding terms (slide 17).

For a new website

3

Extract its distinct terms, with their share of URLs and traffic.

4

A term is important if it is very similar to a library term (Levenshtein ratio > 0.8). It inherits that term's category.

5

Terms on more than 95% of URLs lose their importance: they can't tell groups apart.

Modeling deep dive · 2 Weighted distance

Weighting aligns the distance with business needs

d(a, b) = 1 − Σpart Wpart · Spart(a, b) / Σ Wpart
parts: host · path · query · custom variables
1

Field by field: same host? same value at each path level? how many shared keys, with equal values?

2

Term weights: an important term weighs 0.9, any other 0.1, so matching on product counts 9× more than matching on an ID.

3

Part weights come from the traffic of each part's important terms. The host gets half of the smallest.

4

Bounded in [0, 1]. The full N × N matrix is computed in Rust.

URLs like shop.example/products/1234?some_key=toto||c_key<c_value~page_category<product; important terms: path products, cart; custom variable page_category.

Modeling deep dive · 3 Weighting and the tree

Weighting lifts important terms to the top of the tree

Without weighting · first version

With weighting · second version

Merged last. Two URLs that differ on an important term are far apart, so they merge late: the split on that term sits near the root.

Met first. Walking down from the root, the cut reaches nodes defined by an important term before any noise split, and stops there.

Not guaranteed before. Without weighting, such nodes can sit at the bottom of the tree, and the groups come out fragmented or meaningless.

Modeling deep dive · 4 Tree cut

Cut the tree where important terms define a group

1 · Flag nodes whose rules contain an important term with a single value, e.g. level 1 = cart.

2 · Walk down from the root and stop at important nodes. Branches with none collapse to their highest node.

3 · Select the stopping nodes as page groups: two important ones and one catch-all.

important not important collapsed / ignored selected page group Size guards: > 1 URL or 0.5% traffic, and < 80%.

Modeling deep dive · 5 Rules and category

Describe each group with rules, then label it

Positive and negative conditions

URLs in the group/product/12345 · /product/98761 · /product/55002
Look-alike outside/product/compare?ids=1,2
positivewhat every URL shares: host = shop.example, level 1 = product, level 2 = any
negativewhat excludes the look-alikes: level 2 ≠ compare

Main idea: if a field takes few distinct values in the group, those values become a condition; if it takes many, it becomes a wildcard. An in-house library, autoconda, does this.

Translated into product rules

Path contains "/product/" AND Path does not contain "/compare"

A translation layer turns the conditions into the product's operators. Illustrative example.

Page category: a vote

Collect the categories of the important terms in the group's rules. One category: the group gets it. Several or none: left for the person to choose.

Serving: one stateless API

1

Validate the payload and parse each URL into host, path, query and custom variables (urldata).

2

Score terms against the library; take the person's important terms.

3

Distance matrix in Rust, Ward clustering in SciPy, important-term cut.

4

Rules from autoconda, category vote; return each group with its rules, traffic and URL share, a sample URL and its category.

POST /v1/get_terms URLs → terms + importance POST /v1/get_clusters URLs + terms → page groups POST /v1/get_key_values URLs + key → its values

No weights, no database

The "model" is code plus the curated term library. FastAPI service in one Docker image; Python 3.11 with a Rust extension.

Release with GitOps

Two-stage image build (Rust wheel, then Python) → Harbor registry → version set in the infra repo → ArgoCD.

Recap

Auto-mapping in four ideas

1

An important-term prior

A curated library says which URL terms carry business meaning.

2

A weighted URL distance

Field by field, with important terms weighing 9× more.

3

A tree cut driven by importance

Positive and negative rules

Readable conditions per group, translated into product rules.
